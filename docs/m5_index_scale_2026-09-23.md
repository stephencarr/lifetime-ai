# M5 synthetic ANN capacity experiment — 23 September 2026

The previous 128-claim limit applies only to the retired diagnostic answer path. The model path queries a USearch HNSW index, but it currently rebuilds that index from canonical SQLite state on startup. This experiment measures the ANN component's mechanical capacity; it does **not** measure semantic paraphrase recall, SQLite population or restart cost, answer correctness, account partitioning, or deletion consistency at scale.

The configuration in [`config.json`](../evaluation/m5_index_scale/v0.1/config.json) was hashed in [`freeze.json`](../evaluation/m5_index_scale/v0.1/freeze.json) before the first run. It uses the same 384-dimensional cosine, float16, connectivity-16, expansion-add-128, expansion-search-96 settings as the current model retriever. It incrementally builds 10,000, 100,000, and 1,000,000 seeded synthetic vectors; queries 32 planted vectors per tier at top 24; and measures query time, index size, process memory, build time, and final persisted-index save/load. Random planted-vector recall is a mechanical ANN check, not a source-retrieval metric.

The first attempt is retained at [`attempt-01.json`](../experiments/m5_index_scale/attempt-01.json). It recovered all 32 planted vectors at both 10,000 and 100,000 entries, but only **12/32 at 1,000,000**, so the frozen recall gate failed. At one million, top-24 query p95 was 2.15 ms, the in-memory index was 1.33 GB, peak process RSS was 1.03 GiB, and build time was 393.6 seconds. The persisted index occupied 916.7 MB and loaded in 0.76 seconds; reloaded recall remained 12/32. These are single-process measurements on this machine and do not include SQLite or embeddings.

After seeing that failure, a second configuration changed only HNSW `expansion_search` from 96 to 1024 and kept the same seed, vectors, gates, and other index settings. Its configuration and reason were frozen in [`v0.2`](../evaluation/m5_index_scale/v0.2) before scoring. This is a development tuning attempt, not independent validation. The first configuration and failed result remain retained.

The [second retained attempt](../experiments/m5_index_scale/v0.2-attempt-01.json) also **failed** the predeclared 32/32 planted-recall gate: it recovered 31/32 at one million. Query p95 rose to 17.18 ms, with a 378.0-second build, 1.33 GB reported index allocation, and 1.03 GiB peak process RSS. Reloaded recall remained 31/32, with 19.38 ms p95. The wider search materially improved this mechanical probe, but no current configuration passed. Neither attempt establishes realistic semantic candidate recall or a million-claim product path.

## Scale architecture implied by the experiment

The canonical state remains transactionally stored and source-linked. A production retrieval route must partition by account before search, keep a persisted ANN index and an item-ID mapping synchronized with a durable state-change sequence, and atomically publish an index checkpoint. On startup it must compare the checkpoint sequence with canonical state, replay verified changes or rebuild, and refuse semantic answers while the index is incomplete. Source deletion must remove the item from FTS and ANN before the runtime treats the search view as healthy. Top-k retrieval can answer supported narrow questions only; broad inventory questions need a separate complete filtered enumeration with a completeness marker. As the collection grows, measure semantic candidate recall with realistic distractors and account partitions, not just planted-vector recovery.

The current implementation has query-time HNSW and transactional FTS, but reconstructs the ANN and its Python item-ID mapping from SQLite at startup. It does not yet implement persisted checkpoint replay or tenant partitioning. Both million-vector configurations failed the frozen planted-recall gate. The next development instrument should test partitioned or sharded search with labeled semantic queries, distractors, update and deletion visibility, and recovery costs. Participant UAT and formal G5 remain separate.
